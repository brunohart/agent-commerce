Jev at the Payment Edge
Independent project · not affiliated with Windcave or TypeSafe AI · illustrative priors, not company data

What agentic commerce is worth to a gateway, after everything that breaks

When software starts buying on people’s behalf, a payment gateway gets more transactions, smaller ones, and a set of failures it has never had to price. This project puts Jev, TypeSafe AI’s decision model, at the one point in a payment where a rule cannot decide, for a gateway shaped like Windcave’s (online checkout plus a large unattended estate). Then it breaks the whole thing on purpose and works out what to build and in what order.

The answer the model gives: build storm-proofing, then agent-ready rails, then mandate layer. Agent-ready rails on their own lose money in 85% of simulated worlds, because they bring in the volume and its failure modes together. Micro-settlement is a real option and the model says when to exercise it.

The decision model

Jev estimates. The gateway decides.

Jev is TypeSafe’s first System One model: a model built to make fast, structured decisions that software uses directly. You send it a state and a set of typed questions. It evaluates every question in parallel, each in isolation against the same state, and returns typed answers with probabilities. It does not generate text. A payment gateway needs exactly that: a number it can act on inside a latency budget.

The typed questions are called primitives. There are four, and this gateway uses one of them.

PrimitiveAsksReturnsIn this gateway
NoulIs this statement true?noulUsed twice per agent payment. The value is the probability the answer is yes, which is what an expected-value rule needs.
ChoiceWhich option from a list?choice, probabilities, confidenceNot used. Asking for approve, challenge or decline would put the gateway’s costs inside the model.
ScoreWhere on a rubric?score, probabilities, confidenceNot used. The question is whether, not how much.
BoxWhere in this image?box, confidenceNot used. There is no image in a payment.

Most of an agent payment can be checked by rule. A signature verifies or it does not; a budget is exceeded or it is not. One question cannot: an agent told to do the weekly shop buys a prepaid Visa card at the supermarket checkout. The merchant category matches, the cap is respected, and the cardholder will dispute it. That judgement is one Noul. TypeSafe’s own guidance is to use code where code will do, ask one narrow question per judgement, and combine the answers in code. This pipeline is built that way.

Jev and I disagree on 3 of the 36 borderline items: fee to replace a lost transit card (73%); rideshare trip to the office (19%); e-scooter weekend pass (49%). On at least one of those I think Jev has the better argument, which is the nature of a borderline label.

Its probabilities are underconfident on this set: they sit closer to 50% than the outcomes justify, by a factor of about 2.2 on the log-odds scale. That is the opposite of the failure I had built a test for, and it matters for the same reason: the gateway uses the number as a number. The guard’s recalibration is what corrects it.

Valuation

Expected value, with the Jevons effect priced in

Expected value asks what a bet is worth on average across the worlds you think are possible. Applied to agentic commerce it usually prices today’s transactions with a different payer. That misses the main effect. When the cost of using something falls, more of it gets used. An agent removes most of the effort of a purchase, so purchases multiply and shrink.

count = baseline × frictionRatio ^ −elasticity more transactions ticket = baseline × (count multiplier) ^ −fragmentation smaller ones value(bets) = E[ Σₜ intentsₜ × netPerIntent(bets, agentShareₜ, ticket) × retentionₜ / (1+r)ᵗ ] − build − run

netPerIntent is measured, not assumed. A simulator runs a working payment pipeline against agents, humans and attackers, with 21 failure modes injected, and reports what each combination of controls earns after every failure is paid for. The same expected-value rule that turns Jev’s probability into an action is used here at a five-year timescale.

The guard that matters most is the plainest one. When one call in five returns nothing and there is no fallback, completed agent payments fall from 83% to 65%. With a fallback to the static rule they hold at 82%.

Recalibration comes next, and the measurement is why. Jev’s probabilities are underconfident, so acting on them as stated completes 78% of honest agent payments against 83% once recalibrated, and merchant losses are $97 against $97 per 1,000 intents. Planted text moves merchant losses from $97 to $107, and a drifted alias from $97 to $102. Differences of a few dollars are within the noise of the simulation.

How good does it have to be?

Merchant loss per 1,000 purchase intents, by the model’s skill at telling bad payments from good.

Against the static rule, the decision layer is worth +$0.8m at the skill measured, −⁠$0.5m if it is weak and +$1.0m if it is strong. Without a fallback, during an outage, it is worth −⁠$2.1m.

Most of that value does not come from catching more fraud. It comes from no longer declining honest agents: the static rule turns away about one in twelve, and a calibrated model at these base rates approves nearly all of them, correctly.

The model’s skill shows up in merchant losses. Below an AUC of roughly 0.90 it lets through more than the static rule did. That threshold is measurable in shadow mode before Jev decides a single live payment.

Sequencing

Build order

At each step, add the bet with the largest marginal value given what already exists. The order matters because the bets are complements: what one is worth depends on which others are in place.

  1. Step 1Storm-proofing+$2.3m marginal

    Keep it up: agents retry at machine speed, so ambiguity must be removed.

    Portfolio so far loses money in 0% of worlds.

  2. Step 2Agent-ready rails+$4.6m marginal

    Get the volume: protocols, agent credentials, delegated authentication.

    Portfolio so far loses money in 5% of worlds.

  3. Step 3Mandate layer+$6.9m marginal

    Keep it clean: verify what the human authorised, let Jev judge what rules cannot, keep the proof.

    Portfolio so far loses money in 1% of worlds.

  4. Hold as an optionMicro-settlement−⁠$1.8m marginal

    Unlock the Jevons volume: make a $2 purchase economic for the merchant.

    Portfolio so far loses money in 5% of worlds.

When micro-settlement becomes worth building

Marginal value of adding it to the recommended three (NZ$m), by unattended volume elasticity.

Adding micro-settlement changes the expected value by −⁠$1.8m, and it is the best choice in 9% of worlds. It is the only bet whose value is mostly the Jevons term: plain EV puts it at −⁠$3.3m.

Within the prior range it does not break even on elasticity alone. That is a measurable trigger: run micro-pricing with a handful of charging or parking operators and watch whether session counts respond.

The first version of this model priced aggregation by splitting the fixed fee across the batch. It lost money in every world. The engineering is the easy half of that bet; the pricing is the hard half.

Beyond one gateway

What it would take to be worth a billion

Everything above values the stack on one gateway’s own traffic. That is a feature, and a feature is not worth a billion. It becomes worth more than the product it started in only if other people’s payments run through it. The part that can travel is the conformance receipt: a signed record, issued at authorisation, of the mandate, the pinned model, what it was asked, what it said and what the gateway did. It is committed to an append-only log, so it cannot be written after a dispute arrives.

Today no card network rule says who is liable when an agent buys the wrong thing. Disputes are won or lost on proving what the customer authorised the agent to do. A receipt is that proof. Whether it is worth anything to anyone else depends on whether the rules come to recognise it.

Limits

What this is and is not

  • The inputs are priors, not Windcave figures. Windcave is privately held and I have no inside data. The output is reported per 100M baseline transactions so it scales with real volume and does not pretend to know it.
  • Jev was measured on 234 synthetic labelled payments, not on a gateway’s real disputes, and the borderline labels are mine. The simulator replays those measurements statistically; it does not call Jev for each simulated payment. Latency was measured from a cloud build environment, not from a gateway’s own network.
  • The guard is handed every outcome immediately. In production, labels arrive weeks later and only for approved payments, which makes calibration harder to measure than it looks here.
  • The pipeline is a reference implementation. Mandates are signed with real Ed25519 and the ledger is double-entry with enforced invariants, but it implements none of the live agent-payment protocols and talks to no card network.
  • The dispute thresholds and penalties are illustrative. Each scheme’s monitoring programme has its own definitions.
  • Regulatory liability for agent-initiated payments is unsettled, and the model holds it fixed.
  • The ranking is stable across seeds. The dollar figures move with the priors, which is what the sensitivity chart is for.
